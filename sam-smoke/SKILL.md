# SAM Smoke 灌煙

從程式的每個入口灌煙，看煙實際流到哪裡、在哪裡停下，畫成一份可以逐步播放的 HTML 報告。
目的是讓使用者看懂專案**現在的程式碼**實際怎麼運作，不是它原本規劃成怎樣。

做法是「讀程式碼、寫 `smoke.json`、跑腳本產生 HTML」。**不要自己寫 HTML，不要修改範本。**
畫面由固定範本產生，所以每次長得一樣；你的工作是把 `smoke.json` 的內容寫對。

以下 `SKILL_DIR` 代表這個 SKILL.md 所在的資料夾，執行指令時換成實際路徑。
環境是公司內網，不能連外部網路：不要 `npm install`，腳本只用 Node 內建模組。

## 這個 skill 不做什麼

- 不執行程式、不跑測試。全部靠讀程式碼。
- 不判斷程式碼該不該刪。死路只是「煙走到這裡白走了」的事實，要不要處理由使用者決定。
- 不畫「應該是怎樣」。規格和文件寫了但程式碼沒有的東西，不會出現在報告裡。

## 流程

照順序做，不要跳過。

### 1. 確認範圍

- 專案根目錄：使用者沒說就用目前的工作目錄。
- 輸出位置：預設 `專案根目錄/smoke/`，裡面放 `smoke.json` 和 `smoke.html`。
- `smoke/smoke.json` 已經存在時，讀進來接著做，不要從頭來（見「重新灌煙」）。

### 2. 盤點模組和入口

只讀程式碼和建置設定。先讀 `SKILL_DIR/references/entries.md`，照專案類型找入口。

- 模組：依資料夾和檔案的實際分工，分成 2 到 8 個。名稱用使用者看得懂的詞。
- 入口：程式會從哪些地方被觸發。每個入口歸到一個階段：
  `boot`（啟動）、`run`（待命時被事件觸發）、`exit`（結束）。
- 把全部入口寫進 `smoke.json`，`steps` 先寫空陣列 `[]`。格式見 `SKILL_DIR/references/format.md`。

入口要列完整。這一步漏掉的入口，使用者就永遠不知道它存在。

### 3. 決定先灌哪些入口

- 入口在 5 個以內：全部灌。
- 超過 5 個：把入口清單（依階段分組）給使用者看，請使用者挑。
- 沒有人可以問：灌 `boot` 全部、`exit` 全部，加上 `run` 中程式碼最多的 3 個，並在最後回報時說明選了哪些。

### 4. 逐個入口灌煙

先讀 `SKILL_DIR/references/tracing.md`，這是這個 skill 最重要的文件。

一次只追一個入口：從入口的處理函式開始，**打開每個函式的本體**往下讀，把煙走過的每一步寫進這個入口的 `steps`。
每一步都要有 `file`、`line`、`symbol`，而且是你這次真的打開檔案看到的位置。

### 5. 產生報告

```
node "SKILL_DIR/scripts/render.js" smoke/smoke.json --root 專案根目錄 --out smoke/smoke.html
```

腳本會先檢查，全部通過才輸出。每灌完一個入口就執行一次，不要等全部做完。

### 6. 修正到通過

檢查不通過時，每個問題會列出「哪裡、為什麼、正確寫法、下一步」。
照「下一步」修改 `smoke.json`，重新執行第 5 步，重複到顯示「結果：全部通過」為止。
**沒有顯示「全部通過」就不算完成。**

位置對不上時，重新打開檔案核對，不要只改行號去湊。對不上通常代表那一步是猜的。

### 7. 回報並接著做下一個

回報內容：

1. 報告檔案位置。
2. 每個已灌煙入口的死路和霧，各附 `file:line` 和一句原因。
3. 還沒灌煙的入口清單。
4. 問使用者接著灌哪一個。使用者指定後回到第 4 步。

灌完一個入口不是結束。只要還有沒灌的入口，就要給使用者「接著灌下一個」的選擇。

## 最重要的規則

1. **證據只有程式碼。** 不讀 README、規格、設計文件、commit 訊息來決定步驟。註解和函式名稱只能當線索，不能當依據。
2. **打開本體才能寫。** 沒有打開函式本體讀過，就不能把它寫成一步。`initDevice` 不一定真的初始化了裝置。
3. **看不清楚就畫霧，不准猜。** 函式指標、回呼表、字串組出來的名稱、多個實作的介面，確定不了目標就是霧（`kind: "fog"`）。
4. **死路照走。** 走得到但白走的路（回傳值沒人用、寫了沒人讀）也要畫出來，標成死路（`kind: "dead"`），並寫出證據在哪一行。
5. **每條路的最後一步都要有交代。** 最後一步一定是終點、死路或霧，並寫 `reason`。
6. **不編造順序。** 同一階段的入口沒有先後。步驟的順序是程式碼裡的執行順序。
7. **不改範本、不手寫 HTML。** 畫面有問題時回報給使用者，不要自己改 `assets/template.html`。

## 重新灌煙

程式碼改過之後，直接對舊的 `smoke.json` 執行檢查：

```
node "SKILL_DIR/scripts/check.js" smoke/smoke.json --root 專案根目錄
```

位置對不上的步驟會被列出來。有問題的入口整個重新追蹤（從第 4 步開始），不要只修行號；沒問題的入口保留。
同時重做第 2 步的入口盤點，補上新增的入口，刪掉已經不存在的入口。

## 常見錯誤

- 把函式返回後的下一個呼叫寫成分岔：不用 `from`。煙照執行順序走，`from` 只用在條件分岔和折返。
- 一步切得太細（每個函式呼叫一步）：超過 40 步會被擋下。合併的原則見 `references/tracing.md`。
- 標題寫成函式名稱：標題寫這一步做了什麼（「驗證資料格式」），函式名稱放 `symbol`。
- 霧寫成普通步驟：看到 `ops->xxx()`、`handlers[name]()`、事件匯流排就停下來確認目標。
- 把文件裡的流程照抄進來：報告和文件不一致是正常的，那正是使用者要看到的。

## 檔案

| 檔案 | 用途 |
| --- | --- |
| `references/entries.md` | 各類專案的入口長什麼樣子、怎麼找 |
| `references/tracing.md` | 灌煙規則：一步是什麼、終點、死路、霧、分岔 |
| `references/format.md` | `smoke.json` 欄位與字數上限 |
| `scripts/check.js` | 檢查格式與程式碼位置 |
| `scripts/render.js` | 檢查後產生單一 HTML 檔 |
| `assets/template.html` | 固定範本，不要修改 |
| `examples/` | 範例專案、範例 `sample.json` 與產出的 `sample.html` |
